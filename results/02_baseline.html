02 · Evaluate two transparent baselines¶

Question: How often does the largest standardized mean shift identify the service where a fault was injected?

Both baselines are heuristics, not trained ML models. Their measured failures motivate the later learning problem. All tables are computed below.

1. The rule and evaluation setting¶

For metric $m$, $z_m = |\mu_{post,m}-\mu_{pre,m}|/(s_{pre,m}+10^{-8})$. A service's score is the maximum of its metric scores. We use sample standard deviation ($ddof=1$), all available time < inject_time rows, and all available time >= inject_time rows. Ties use alphabetical order.

  • zscore keeps every metric.
  • zscore_nonconst ignores metrics whose normal-window standard deviation is exactly zero. For those, the denominator is just $10^{-8}$, so any blip after injection gets an enormous score (see notebook 01, section 6).

Injection time is supplied. No root labels, fault labels, case names, or future cases are input features. Full post-injection recordings are available, so this experiment is offline localization, not online incident detection or a held-out learned-model test.

2. Read the metrics correctly¶

AC@k is the fraction of cases with the annotated root in the first k positions. Avg@5 is the mean of AC@1, AC@2, AC@3, AC@4, and AC@5; it is not average precision or mean reciprocal rank.

all_cases includes all 125 supplied cases, counting invalid-window cases as misses. evaluable_only reports the 123 cases with valid windows. Both denominators are shown to prevent silent dataset exclusions. The chart compares both baselines per fault type on all 125 cases.

4. Explain two failures using actual measurements¶

The following Markdown notes were generated from this pinned dataset's measured zscore_nonconst scores. The verification cell below checks that they still agree with the recomputed worst cases. Interpretations are hypotheses.

Two measured baseline failure cases¶

re1ob_checkoutservice_loss_1¶

The annotated root checkoutservice ranks 5. The services/candidates above it are paymentservice, recommendationservice, cartservice, productcatalogservice.

service winning_metric score pre_std_of_winner
paymentservice latency-90 377.07 2.8107e-05
recommendationservice mem 191.56 1183.6
cartservice latency-90 144.7 9.34e-05
productcatalogservice latency-90 59.02 6.0153e-06
checkoutservice mem 20.336 1.4034e+05

Observed: the maximum standardized mean shift is larger for these candidates. Possible explanation: packet loss can affect callers and request/error metrics, while unrelated resource drift can also score highly. The heuristic does not model dependencies or temporal propagation. These measurements alone do not establish which non-root changes were caused by the injected fault.

5. What comes next¶

Ignoring constant metrics was the first scaling fix; next try robust scaling (median/MAD) and other aggregations as stronger statistical comparisons. Then learn an anomaly representation and compare a service-independent ranker with a graph model using a verified dependency graph. Divide training and testing by whole incidents; later reserve an entire application for cross-system testing. Do not randomly split rows from one recording across training and testing.

A learned GNN, cross-system test, Docker, Kubernetes, and new fault-injection runs are not implemented this week. BARO is optional and not reproduced in this environment; see the README for the package-compatibility reason.

Outputs in results/, for each method zscore and zscore_nonconst: <method>_per_case.csv, <method>_summary.csv, <method>_protocol.json, <method>_worst_cases.csv; plus fig_baseline_comparison.png.
